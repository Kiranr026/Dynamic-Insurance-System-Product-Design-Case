01 / Foundation

Visualization Principles

Six non-negotiable principles govern every chart, table, and data display in DIS. They are not aesthetic preferences — they are design constraints that ensure a safety-critical, financially sensitive system communicates accurately and trustworthily.

01
Insight Over Raw Data

Users and admins should never see raw telemetry values — G-force readings, RPM numbers, or engine load percentages are meaningless to most users. Every data point must be translated into an outcome before it's displayed.

Applied: OBD data → normalized 0–100 score. Score → premium impact in rupees. Claim score → plain-language settlement explanation.

Driving: "Smoother braking this week" not "G-force delta: −0.4m/s²"
02
Simplicity Over Density

A chart that requires 30 seconds to understand has failed. DIS users check their score daily — the interaction must be under 5 seconds. Admin users process high volumes — density is acceptable, but only with strong visual hierarchy.

Applied: Driver dashboards: max 3 visible metrics above fold. Admin dashboards: dense tables permitted with strong sorting, filtering, and progressive disclosure.

Insurance: One breakdown card not 12 line items on the home screen
03
Context Before Detail

Before showing a number, show its meaning. Before showing a chart, show its headline. The user should understand the significance of data before they explore it — not after.

Applied: Score breakdown always leads with the composite score, then reveals the factors. Claims show the settlement amount before the adjustment calculation. Premium shows final amount before the breakdown.

Risk evaluation: "Excellent Driver" badge before the score bars are shown
04
Consistency Across Views

If green means "safe" in the driving score chart, green must mean "safe" everywhere — in tables, badges, notifications, and admin panels. Color inconsistency destroys trust in a system where color communicates financial risk.

Applied: Same semantic color palette system-wide. Score tiers have identical color-to-meaning mapping in driver, insurer, and MVD views. Never use success-green for a decorative purpose.

Risk levels: teal (excellent) → green (good) → amber (moderate) → red (high)
05
Highlight Anomalies and Risks

The system's most valuable function for admins is surfacing what is unusual. A driver whose score suddenly drops 30 points in a day, a claim submitted for a date where blockchain shows no trip data — these anomalies must visually demand attention.

Applied: Anomaly rows flagged with red left-border in tables. Score deviation charts mark statistical outliers with a distinct dot and tooltip. Fraud detection flags appear as high-contrast warning banners at the top of the claim detail.

Admin: Flagged rows break the visual rhythm intentionally to demand review
06
Trustworthy by Design

Every chart must make the user feel the system is honest, not trying to hide anything. Truncated Y-axes, misleading scales, and cherry-picked time ranges erode trust in a financial platform. All data has a verifiable source.

Applied: Score charts always start Y-axis at 0. All charts show data coverage: "Based on 14 trips this month." Blockchain verification badge always appears adjacent to score displays.

Blockchain: Every score chart shows "Verified record" indicator in the legend
02 / Strategy

Key Data Types to Visualize

Driving Behavior Data

  • Why critical: The raw input — OBD feeds speed, braking G-force, acceleration rate, and engine load per trip
  • Visualization form: Normalized 0–100 progress bars by factor; behavior event markers on trip timeline
  • Decisions it supports: Which specific behavior to improve; whether a trip score was fair; daily habit formation
  • Audience: Driver (simplified) + Insurance admin (detailed)

Driving Score Trends

  • Why critical: The key engagement metric — users return daily to check their score trajectory
  • Visualization form: 7-day bar chart (color-coded by tier), 30-day line chart with moving average
  • Decisions it supports: Premium forecasting; habit improvement tracking; streak maintenance motivation
  • Audience: Driver (primary) + Insurer (risk assessment)

Insurance Premium Changes

  • Why critical: Direct financial impact — must be completely transparent and understandable
  • Visualization form: Waterfall breakdown card; premium vs. score interactive slider; month-over-month bar comparison
  • Decisions it supports: Whether to renew; whether to improve score before renewal; which insurer to choose
  • Audience: Driver (understand pricing) + Insurer (revenue management)

Claims Data

  • Why critical: Highest-stakes data — wrong interpretation leads to financial loss or fraud
  • Visualization form: Timeline tracker (driver); claims queue table (admin); settlement breakdown card
  • Decisions it supports: Approve/reject/query; fraud detection; settlement amount validation
  • Audience: Driver (track status) + Insurer admin (process decisions)

Risk Levels and Predictions

  • Why critical: Predictive layer — identifies high-risk drivers before accidents happen
  • Visualization form: Risk tier distribution donut chart; driver risk table with color-coded badges; trend alert cards
  • Decisions it supports: Premium surcharge application; fraud flag prioritization; enforcement action by MVD
  • Audience: Insurer admin + MVD (primary consumers)

Aggregate / Population Data

  • Why critical: The regulatory and strategic layer — enables policy decisions and road safety analysis
  • Visualization form: Region heatmap; score distribution histogram; year-over-year trend lines; compliance rate bars
  • Decisions it supports: Road safety policy; enforcement resource allocation; insurance market pricing
  • Audience: MVD / Government (exclusive)

When to use Heatmaps
  • Identifying patterns across time: "bad score days" cluster on certain days of the week
  • Score calendar — 30/90-day view of driving consistency
  • Admin: regional risk maps, time-of-day accident heatmaps
  • Never use heatmaps for precise value comparison — they encode magnitude, not exact figures
✓ Chart Selection Do's
  • Use line charts when time is the X-axis and change is continuous
  • Use bar charts for discrete buckets — days, trips, behavior factors
  • Use radial/gauge exclusively for single bounded metrics (score ring)
  • Use tables when exact values and comparison of many attributes matter
  • Always include a plain-language summary below or above every chart
✕ Chart Selection Don'ts
  • Never use pie charts for behavioral data — part-to-whole is misleading here
  • Never truncate Y-axis — especially when showing score trends (builds mistrust)
  • Never put more than 2 lines on one line chart — causes confusion
  • Never use 3D charts — they distort perception in insurance/financial contexts
  • Never use a chart when a single number (e.g., "84.1%") communicates it better

Visual Hierarchy & Semantic Color

Data Priority Hierarchy

P1
Primary — Composite Score / Premium
Large serif font, 48–72px, most prominent element on page, always above fold
P2
Secondary — KPIs and Factor Scores
Medium size, visible in KPI row, score breakdown bars, premium components
P3
Tertiary — Trend Charts and History
Supporting context below fold or on secondary screens
P4
Raw Data — Tables and Full Records
Accessible via drill-down only — never on the primary screen

Semantic Color Rules — Non-Negotiable

Teal → Excellent (≥80%)
Best performance, maximum discount
Green → Good (70–79%)
Safe driving, discount applied
Amber → Moderate Risk (60–69%)
Full price or minor surcharge
Red → High Risk (<60%)
Premium surcharge, fraud review
⚠️
Critical Color Rule
Red (danger) must never appear on a dashboard for a reason other than high risk or error. Using it for section headers, hover states, or decorative purposes destroys its communicative value the moment a real high-risk alert fires. Blue (brand) and gray are the only safe decorative colors.

Tooltip Design Rules

  • Trigger on hover (desktop) or tap (touch) — never on click for primary charts
  • Show the date/context first, then the value, then the breakdown
  • Max 5 rows in a tooltip — anything more should be a drill-down page
  • Tooltip must not obscure the chart area — position dynamically
  • Always include the financial impact (premium) when showing a score tooltip
  • Close on mouse-out after 200ms delay — prevents flickering
05 / Strategy

Data Simplification Techniques

Raw data from OBD systems is incomprehensible to most users. The transformation pipeline from raw sensor data to actionable insight is a core design responsibility — not a backend concern.

Raw → Insight Translation

✕ Raw (never show)
G-force X-axis: −0.41m/s², Y-axis: 0.07, braking event duration: 2.3s
↓
✓ Insight (always show)
You braked suddenly 3 times today — this reduced your braking score by 4.2 points

Comparative Framing

✕ Absolute (less meaningful)
Score: 84.1 out of 100
↓
✓ Contextual (motivating)
84.1% — your best score in 6 weeks. ↑ 4.3 points vs last week. 1 point from your all-time best.

Financial Translation

✕ Technical (not actionable)
Driving score: 84.1% → tier: Excellent → multiplier: 0.75
↓
✓ Financial impact (actionable)
Your score saves you ₹1,689/month. Improving braking alone could save you an additional ₹280.

Progressive Disclosure — How Much to Show and When

Level 1 — Glance (0–3 sec)
Score + Status + Delta
84.1% · Excellent · ↑4.3 this week. User gets the full picture in under 3 seconds without reading anything.
Level 2 — Scan (5–15 sec)
Factor Bars + One Insight
Speed 88, Braking 71 ⚠, Acceleration 82. One call-to-action insight: "Improve braking to unlock higher discount."
Level 3 — Read (30 sec+)
History + Trip Data
30-day chart, individual trip breakdown. Accessed via "View Details" — never shown by default on dashboard.
Level 4 — Investigate
Raw Blockchain Record
Block timestamp, verification hash. Accessible via "Verified Record →" link. Never shown unsolicited.
06 / Strategy

Real-Time vs Historical Data

Real-Time Data — Visual Treatment

  • Definition: Score updates after a trip (within 2–4h), OBD connection status, claim status changes, active alerts
  • Visual signals: Animated dot indicator (pulsing green), "Live" or "Updated X mins ago" timestamp, subtle teal left-border on cards
  • Interaction: Auto-refreshes silently — user never manually refreshes. Score change notification triggers in-app banner
  • Never: Show a loading spinner when real-time data is updating — use a progress indicator that doesn't interrupt the existing content
Live · Score updated 12 minutes ago
Based on this morning's 22km trip to MG Road

Historical Data — Visual Treatment

  • Definition: Score trends, premium history, trip records, past claims, blockchain archive
  • Visual signals: Date range selectors, "As of [date]" labels, muted opacity for past periods, calendar heatmaps
  • Interaction: User-controlled date range filters, drill-down from trend to specific day to specific trip
  • Never: Mix historical and real-time data in the same chart without a clear visual separator or legend entry distinguishing them

07 / Strategy

Interaction Design & Edge Cases

Filter & Drill-Down Interactions

  • Date range picker: Presets (7d, 30d, 90d, Custom) + date range selector. Applies to all charts on the screen simultaneously
  • Trip type filter: All / Only flagged / Excellent only — chip selector above charts
  • Drill-down: Click any bar → opens trip detail drawer from right. Click any table row → same. Never a full page reload.
  • Admin segment filter: Risk tier (All/High/Moderate/Low), region, date, premium bracket
  • Sort: Click column header to sort. Active sort column highlighted with arrow indicator

Empty, Incomplete & Error States

  • No trips (new user): Illustrated empty state with "Drive today to see your first score" — never a blank chart area
  • Incomplete data (OBD disconnected mid-trip): Bar shown with hatched pattern and "Incomplete trip" tooltip. Score not calculated from partial data.
  • Score sync pending (blockchain not yet committed): Score shown with "Pending verification" dotted border — not hidden, clearly labeled
  • Data error (corrupted OBD file): Row flagged with orange icon + "Data quality issue — excluded from score" tooltip. Never silently dropped.
  • Admin — no claims: "All clear" empty state with green background. Different tone from a user empty state.
🎯
Interaction Design North Star
Every interaction with data should make the user feel more informed, not more confused. If a filter, drill-down, or tooltip requires the user to re-orient themselves before understanding what they're looking at, the interaction has failed. Context must survive all navigation transitions.

Role-Based Access Control

  • Driver: Read/write own data only. No access to other drivers, insurer admin, or MVD
  • Insurer admin: Read all drivers in portfolio. Write claims decisions, premium adjustments. No access to MVD data
  • MVD officer: Read-only. Aggregate data by default; individual lookup requires justification logged to audit trail
  • Super admin (DriveSure): Full access with elevated audit logging. All actions require 2FA confirmation
  • Role assignments managed by org-level admin only — never self-assigned

Performance & Scalability

  • Pagination: All tables paginate at 50 rows. Infinite scroll not used (breaks bulk selection)
  • Virtual scrolling: Long trip lists (1000+ rows) use windowed rendering
  • Lazy loading: Charts load after critical KPI metrics — users see numbers first
  • Real-time updates: WebSocket for score changes and claim status updates. No manual refresh required
  • Large exports: CSV/PDF exports run as background jobs — user notified via notification bell when ready

Admin UX — Dense but Not Cluttered

  • Tables use compact row height (40px) with expandable rows for detail — not separate pages
  • Bulk actions (approve all selected, export filtered) are always visible when rows are selected
  • Critical actions (Approve, Reject) require one confirmation click — not a separate dialog for routine actions
  • Fraud-flagged rows visually break the rhythm with a red left-border — forces attention even when scanning quickly
  • All dashboard KPIs link directly to their underlying table — click a number, see the data behind it

Data Security in UI

  • PII (full name, phone) is partially masked in table views (e.g., "Ar*** N***") — expanded only on row-level access
  • Blockchain record hashes shown only in dedicated blockchain detail view — never in main tables
  • Session timeout after 30 minutes of inactivity — form data preserved with autosave before redirect
  • All destructive actions (delete, reject, fraud flag) require the admin to type a short justification reason — prevents accidental bulk actions
System Philosophy
"The best data visualization is the one that makes the right decision obvious, not the one that impresses with complexity. Every chart should make someone say 'I understand' — not 'I need to study this.'"
