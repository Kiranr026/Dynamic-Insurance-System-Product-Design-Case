01 / Foundation

Design Principles & Visual Direction

Six core principles govern every visual and interaction decision. They are not aesthetic preferences — they are functional constraints that ensure a data-heavy, trust-sensitive product remains usable, clear, and credible.

01 — Clarity Over Decoration

Every visual element must earn its presence. Data-heavy dashboards fail when decoration competes with information. In DIS, driving scores, premium amounts, and claim statuses are the content — the interface exists only to deliver them without interference.

Applied: Minimal ornamental elements; whitespace as a clarity tool; no gradients on data-bearing surfaces; chart colors encode meaning, not aesthetics.

02 — Data-First Hierarchy

In a system where a single number (the driving score) directly affects someone's finances, that number must dominate the visual hierarchy. Supporting data is secondary. Navigation is tertiary. The system's job is to put the right number in front of the user, large enough to read instantly.

Applied: Score displayed at 2–3× the size of surrounding labels; premium amounts in display type; critical alerts use semantic color exclusively — never decorative.

03 — Consistent Predictability

Users interacting with insurance and financial data need a system that behaves identically every time. Surprise in a financial interface creates anxiety. Components must look, feel, and behave the same regardless of which screen they appear on.

Applied: Single button system with no one-off variants; all status badges follow one pattern; error states use the same visual language system-wide; spacing is always a multiple of 4px.

04 — Trust Through Transparency

Financial and algorithmic decisions must be visually legible. A premium amount shown without context breeds distrust. A blockchain verification shown as a confusing icon adds no trust. The design system provides components specifically designed to make automated decisions feel explainable.

Applied: Premium Breakdown Card component; Blockchain Verification Badge with plain-language tooltip; score explanations surface inline, not buried in a menu.

05 — Accessibility & Inclusivity

An insurance platform serves all demographics including older adults, users with low vision, and users on low-end devices. Every component is designed to meet WCAG 2.1 AA as a minimum, with AAA targets for critical data paths. Color alone is never the only information carrier.

Applied: All text on colored backgrounds tested for 4.5:1 contrast; every interactive element has a visible focus state; icons accompanied by text labels; no information conveyed by color alone.

06 — Purposeful Motion

Animations in a financial platform must serve a function: confirming a state change, drawing attention to critical data, or smoothing a cognitive transition. Motion is never decorative. It never delays the user from seeing information they need.

Applied: Score ring animation (confirm update), skeleton screens (manage expectation), success checkmarks (confirm payment). All animations under 400ms. Respects prefers-reduced-motion.

Visual Direction & Brand Tone

Visual Tone

Modern institutional. Not banking-cold. Not startup-playful. Think: the clarity of a Bloomberg terminal with the warmth of a well-designed insurance statement. Navy and white as structural foundation, with teal and green as behavioral reward signals.

Emotional Feel

Secure: strong structural grid, consistent component behavior. Intelligent: data visualized with precision. Controlled: user always sees the full picture. Transparent: every number has a source. Together these emotions translate into trust.

What DIS is Not

  • Not a consumer app — no playful rounded corners everywhere
  • Not a banking product — warmer, more personal than pure fintech
  • Not a raw data dashboard — always human-translated, never raw output

Why Serif for Headlines?

Libre Baskerville signals institutional authority — the same visual language used by established financial and legal institutions. It builds immediate subconscious trust. Used only for display and H1–H2; lower hierarchy uses Outfit to maintain readability at smaller sizes.

Why Monospace for Data?

Monospace fonts ensure all characters have equal width, making numeric data visually comparable across rows and columns. ₹5,311 and ₹12,000 align perfectly in a monospace table — critical for premium comparisons and claim history tables. Never use a proportional font for tabular numeric data.

04 / Foundation

Spacing & Layout System

A strict 4px base grid. All spacing values are multiples of 4px, ensuring visual rhythm and mathematical harmony. This prevents the "pixel creep" that makes interfaces feel inconsistent at scale. All layout decisions use 8px as the working unit minimum.

Layout Grid — Web

  • Max content width: 1280px
  • Dashboard layout: 12-column grid, 24px gutters
  • Sidebar width: 265px (fixed)
  • Content area: Fluid, max 1015px
  • Card columns: 4 (desktop), 2 (tablet), 1 (mobile)
  • Page padding: 40px left/right (desktop)

Border Radius Scale

  • --r-sm (4px): Badges, tags, small chips, table row highlights
  • --r (8px): Cards, inputs, buttons, dropdowns — the default
  • --r-md (12px): Large cards, modals, premium breakdown cards
  • --r-lg (16px): Drawers, panels, feature cards
  • --r-xl (24px): Score ring container, highlighted stat panels
  • --r-full (9999px): Pills, badges, toggle switches

07 / Guidelines

Data Visualization Guidelines

Use Bar Charts When

  • Comparing values across a discrete time period (weekly/monthly score comparison)
  • Showing distribution of scores across a driver population (insurance admin)
  • Colors encode: green ≥70%, amber 60–70%, red <60%
  • Maximum 7 bars before switching to a line chart

Use Line Charts When

  • Showing continuous trend over time (30-day score history)
  • Multiple metrics on the same timeline (score vs. premium trend)
  • Annotate key events (score milestone, premium change) with a dot and tooltip
  • Never more than 2 lines on one chart to prevent confusion

Use Radial Charts When

  • The driving score ring — single metric, instantly readable
  • Overall completion percentage (e.g., 80% of habits completed)
  • Never use for comparing multiple data series
  • Always show the numeric value at center — ring alone is not enough
✓ Do
  • Translate every chart into a plain-language insight below it: "You drove 18% smoother this week"
  • Use color semantically: green for safe, amber for moderate, red for risky — consistently
  • Show the takeaway first, chart second — users read headlines, not axis labels
  • Always include a legend when color encodes meaning
  • Keep chart titles short: "Weekly Score" not "7-Day Aggregated Driving Performance Metric"
✕ Don't
  • Don't show more than 3 data series on one chart — use separate charts
  • Don't use pie charts for behavioral data — they make comparison impossible
  • Don't show raw OBD values (G-force, RPM) in driver-facing charts — always normalize to 0–100
  • Don't use rainbow color schemes — only the semantic palette (green/amber/red)
  • Don't add gridlines where they aren't needed — they add noise without value

Keyboard Navigation

  • All interactive elements reachable by Tab key
  • Enter/Space activates buttons
  • Escape closes modals, dropdowns
  • Arrow keys navigate within menus and tabs
  • Focus trap within modal when open

Focus States

  • All interactive elements have a 3px offset focus ring: box-shadow: 0 0 0 3px rgba(15,76,129,0.25)
  • Focus visible even on colored backgrounds
  • Never remove outline without replacing it
  • Skip-to-main-content link as first focusable element

Screen Reader Support

  • All icons have aria-label when used without text
  • Score ring SVG has aria-valuenow, aria-valuemin, aria-valuemax
  • Form errors associated to inputs via aria-describedby
  • Status changes announced via aria-live regions
  • Charts have summary text alternatives

Token Architecture for Multi-Platform Scaling

Tokens are stored in a JSON format that can be consumed by any platform — CSS custom properties for web, Figma Variables for design, Swift/Kotlin constants for mobile. The same token color.success maps to #1A7A4A in CSS, the same hex in Figma, and UIColor(hex: "1A7A4A") in iOS. One change in the token file propagates everywhere simultaneously.

Tool stack: Figma Variables (design) → Style Dictionary (transform) → CSS Custom Properties (web) / Swift constants (iOS) / XML resources (Android).

11 / System

Usage Guidelines & Governance

✓ Do — Usage Rules
  • Always use a component from the library before creating a custom one
  • Use semantic color tokens for all color decisions — never hard-code hex values
  • Follow the spacing scale — only values from the defined scale are acceptable
  • Test every new component against all 4 states: default, hover, active, disabled
  • Add aria labels to all non-decorative icons before they ship
  • Accompany every score display with the directional delta (↑ / ↓)
  • Test at 200% browser zoom before any component is marked ready
✕ Don't — Violations
  • Don't create one-off button styles outside the button component
  • Don't use Danger red for non-error, non-risky-behavior contexts
  • Don't use proportional fonts for numeric data in tables
  • Don't skip focus states to "clean up the design" — they are mandatory
  • Don't show blockchain block hashes or raw telemetry values to end users
  • Don't place two primary CTAs on the same screen
  • Don't add new semantic colors — extend existing ones with new shades first

Versioning Policy

  • Patch (v1.0.x): Bug fixes, accessibility fixes, documentation updates — no breaking changes
  • Minor (v1.x.0): New components, new tokens — backward compatible
  • Major (vX.0.0): Breaking changes, token renames, component API changes — requires migration guide

Review Process

  • New components require: design review, accessibility audit, developer review
  • All new tokens require a use-case justification — no token without a named purpose
  • Quarterly design system audit: remove unused components, update deprecation notices
  • Any deviation from the system requires a documented exception with a plan to reconcile

Contribution Guidelines

  • Propose new components in the design system issue tracker with a use-case
  • Components must appear in ≥3 places before being added to the library
  • All contributions must include Figma specs, HTML/CSS implementation, and accessibility notes
  • Product-specific components (Score Ring, Blockchain Badge) are flagged as domain-specific and not generic
System Philosophy
"A design system is not a collection of components. It is a shared language between design and engineering that allows a complex product to grow without fragmenting visually or technically. The goal is not control — it is consistency without constraint."
