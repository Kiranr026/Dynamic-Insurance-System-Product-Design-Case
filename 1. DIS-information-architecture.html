01 / Foundation

IA Strategy & Approach

The DIS IA uses a Hybrid Task-Based + Data-Driven model. Task-based for drivers (they come with goals: check score, pay premium, file claim). Data-driven for insurers and MVD (they explore dashboards, filter populations, audit records). The same underlying data layer serves both mental models without exposing complexity to the wrong user.

🧠
Core IA Decision
One platform, three role-adjusted views. Global navigation structure stays consistent. Content density, default views, and available actions differ per role. This reduces development complexity while maintaining UX clarity for each user type.

Cognitive Load Reduction

  • Progressive disclosure: ML complexity hidden by default, accessible on demand
  • Primary action (score check) always reachable in ≤2 clicks
  • Blockchain data abstracted as "verified" badges — no raw hashes shown to drivers
  • Insurance math expressed as plain-language summaries, not formulas
  • Jargon-free labels throughout (no "OBD telemetry" — just "Driving Data")

Role-Specific Clarity

  • Drivers: Score-first, reward-forward, simplified insurance view
  • Insurers: Risk-first, population dashboards, claims workflow
  • MVD: Compliance-first, read-only audit trail, aggregate analytics
  • Each role has a distinct "home base" — the screen that anchors daily use
  • Cross-role collaboration points clearly defined (claim verification, data sharing)

Scalability Principles

  • Section-based IA — new features slot into existing sections, not new top-levels
  • Notification layer is global, not embedded in one section
  • Settings separated from functional content — never mixed in
  • Admin panels isolated from driver-facing structure
  • AI insights treated as a layer, not a section — can be added anywhere

Why Hybrid IA?

Pure task-based IA breaks down when users also want to explore data (e.g., a driver curious about their historical score pattern). Pure data-driven IA overwhelms casual users who just need to pay a premium. The hybrid model gives every user the right entry point while keeping the underlying structure unified and maintainable.

IA Constraints Addressed

  • Blockchain data is real-time but immutable — IA reflects this with "view-only" history sections
  • ML scores change daily — dashboard is the live anchor, always current
  • Insurance policies have complex legal structures — simplified into 3-zone layouts
  • Claims involve multiple parties — IA provides shared status views

06 / Role Architecture

Role-Based Architecture

The underlying sitemap is shared. What changes per role: default landing page, primary navigation labels, data density, available actions, and which sections are visible or hidden.

🧑Driver
🏢Insurance Co.
🏛️MVD / Gov.

Home Base

Dashboard — score-first, personal, action-oriented. Everything revolves around "how am I driving?" and "what does it cost me?"

Primary Navigation

  • Dashboard · My Score · Insurance · Claims · Rewards
  • Simple, task-based labels
  • No admin sections visible
  • Blockchain abstracted as "Verified" badge

Data Density

Low-to-medium. Scores as percentages, premiums as amounts, trends as sparklines. Technical data (OBD, ML scores) never shown raw — always translated into plain English.

Home Base

Risk Dashboard — portfolio-level view. Distribution of risk scores across all insured drivers. Claims pending. Revenue by tier. High-risk alerts at top.

Primary Navigation

  • Risk Dashboard · Customers · Claims · Analytics · Settings
  • Business-oriented labels replacing personal labels
  • Access to all driver records (read)
  • Claims approval workflow visible

Data Density

High. Score distributions, claim ratios, risk tier percentages, fraud flags. Tables, filters, and export functions prominent. Blockchain records shown with block details for audit.

Home Base

Road Safety Overview — population analytics, region maps. Purpose is monitoring, enforcement, and policy-making — not transaction management.

Primary Navigation

  • Safety Overview · Driver Lookup · Compliance Reports · Settings
  • Read-only access — no transaction actions
  • Cannot modify any data — only view & export
  • Aggregate data only, not individual PII by default

Data Density

Medium-to-high. Aggregate statistics, geographic heat maps, trend lines over quarters. Individual driver lookup available by vehicle registration for specific enforcement cases only.

What Stays Consistent Across All Roles

Navigation Pattern

Top navigation bar with utility icons (notifications, settings, profile). Back navigation always consistent. Notification layer identical.

Design Language

Same color system, typography, and component patterns. Only data density and actions differ. A driver who becomes an admin finds the interface familiar.

Score Data Layer

Blockchain-verified score is the common truth across all roles. All three roles see the same underlying score data — just in different contexts and with different permissions.

07 / Data Architecture

Data & Feature Relationships

The driving score is the central data node. Everything downstream depends on it. Understanding these dependencies is essential for designing a coherent IA where changes in one section logically propagate to others.

🔗
Core Data Flow
OBD Device → Driving Score (ML) → Blockchain Record → Insurance Premium → Claim Settlement. Each stage is both a data producer and consumer. The blockchain is the immutable anchor at the center.
📡
OBD Device
Speed, RPM, acceleration, engine load — raw telemetry
CSV Upload
🤖
ML Model
Random Forest classifier → driving score 0–100%
Score Push
⛓️
Blockchain
Hyperledger Fabric — immutable, verified record
Score Read
🛡️
Insurance Engine
Premium multiplier applied based on rolling average score
On Claim
📋
Claims Engine
Incident-day score retrieved, settlement calculated automatically

Cross-Section Dependencies

  • My Score → Insurance: Score changes trigger premium recalculation shown in Insurance section
  • Insurance → Claims: Active policy required before claim submission is enabled
  • Score → Claims: Incident-day score automatically pulled from blockchain when claim date entered
  • Rewards ← Score: Score milestones trigger token generation, reflected in Rewards section
  • Blockchain → All: Verification status propagates to My Score, Insurance, and Claims — all show "Verified" state

IA Implications of Dependencies

  • Premium display in Insurance must always pull live score data — no stale cache
  • Claims form must be blocked if no active policy exists — with a clear path to Insurance section
  • Dashboard must aggregate from 4 data sources: score, blockchain, insurance, claims
  • Notifications are the cross-cutting layer — triggered by events in any section
  • Settings → OBD connection status affects whether My Score can display real data
08 / Future-Proofing

Scalability & Future-Proofing

The IA is designed as an open framework, not a closed structure. New capabilities slot into existing sections rather than creating new top-level items, preserving navigation simplicity as the product grows.

🤖
AI Recommendations
Delivered as insight cards within My Score and Dashboard Zone 3. AI is a layer on existing sections — not a standalone "AI" section. This prevents cognitive fragmentation.
⚡
Real-Time Alerts
The Notifications utility layer already supports real-time events. Adding push for live score drops or claim updates requires no IA change — just notification type expansion.
📱
Multi-Device Integration
Settings → My Vehicle supports multiple vehicle profiles. Score aggregation logic handles multi-device OBD. IA needs no restructuring — just additional records in existing sections.
🌐
Multi-Insurer Marketplace
Insurance → Renewal already contains "Compare offers." A full marketplace feature extends this sub-page — no new primary nav item needed. Complexity grows within the section.

What Will Never Need Restructuring

  • Primary navigation labels — they're activity-based, not feature-based
  • Dashboard as home base — it's an aggregator, infinitely expandable via zones
  • Utility nav pattern — notifications/settings/profile is a universal web convention
  • Role-based access model — new roles (e.g., fleet manager) slot into existing pattern
  • Blockchain as trust layer — abstracted, not surfaced, so tech changes don't affect IA

Planned Future Extensions (Pre-Accommodated)

  • Fleet Management: New role variant — same IA, fleet-level aggregation
  • Telematics History: Trip History sub-page in My Score already exists
  • Smart Contract Claims: Claims section already handles status tracking
  • Carbon Score: New metric card in Score Breakdown, not a new section
  • API Partner Access: Admin-level portal extension, isolated from user IA
09 / Naming System

Naming & Labeling System

Every label in the system follows three rules: it describes the user's goal (not the system's function), it uses the simplest possible word, and it remains consistent wherever it appears in navigation, headings, and notifications.

✍️
Naming Principle
"My [thing]" pattern for personal data. Active verbs for actions. Never technical system terms as labels. A driver should never need to understand how blockchain or ML works to navigate the platform.

Consistency Rules

  • Same label in nav, page heading, notification, and URL slug
  • "My Score" in nav = "My Score" as H1 = "your score" in body copy
  • Never switch between "claim" and "case" — pick one and hold it
  • Numbers always with units: "84.07%" not "84.07 score"

Tone by Section

  • Dashboard: Warm, motivating ("Good driving this week!")
  • Insurance: Clear, confident, no fine print language
  • Claims: Direct, calm, empathetic — never bureaucratic
  • Admin Portals: Professional, precise, data-forward

Status Labels

  • Claim statuses: Submitted → Under Review → Approved → Settled
  • Score tiers: Excellent (80%+) · Good (70–80%) · Fair (60–70%) · Needs Work (<60%)
  • Policy statuses: Active · Expiring Soon · Expired · Pending
  • Blockchain: Verified · Pending Sync · Not Yet Verified
Summary Principle
"The best IA is the one the user never thinks about. They simply find what they need, complete their task, and leave feeling understood."
This IA hides OBD complexity behind "Car Connected," blockchain behind "Verified," and ML behind "Your Score." Three distinct user types navigate a single coherent system without confusion. That is the goal.
